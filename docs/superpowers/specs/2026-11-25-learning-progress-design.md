# 贝贝单词：基础学习进度持久化设计

日期：2026-11-25

## 1. 目标与原因

当前小程序已经有登录、词库、单词卡、收藏、生词本、错题本、闯关、统计和好友 PK 等页面，但“已学习”和“错词已掌握”仍保存在微信本地缓存。清理缓存或更换设备后会丢失，而且个人统计混合了本地状态与 MySQL 数据。

本阶段先在开发电脑的 MySQL 中保存登录用户的学习进度，完成可重复调试的基础闭环。未来部署到阿里云时保持相同表结构和接口，只替换数据库与服务地址配置。

## 2. 本阶段范围

### 目标

- 登录用户标记单词“已学习/未学习”后，状态保存到 MySQL。
- 登录用户标记错词“已掌握/未掌握”后，状态保存到 MySQL。
- 错词只由好友 PK 和闯关模式中的错误答案产生；普通单词学习不自动加入错题本。
- 首页数量、词库筛选、单词卡状态、错题本筛选和个人统计使用同一份服务端数据。
- 重启后端、重新编译小程序、清除小程序本地缓存后，重新登录仍能恢复进度。
- 不破坏已有收藏、生词本、错题收录、闯关、打卡和 PK 数据。
- 本机后端继续使用 8081 端口。

### 非目标

- 本阶段不开发 AI 功能。
- 不实现间隔重复算法、每日学习计划或复杂熟练度等级。
- 不重做现有页面 UI。
- 不迁移设备中已有的“已学习”和“错词已掌握”本地缓存；升级后以 MySQL 为准重新累计，只保留现有四级、六级单词词库及已有服务端业务数据。
- 不迁移到阿里云，不配置域名、HTTPS、对象存储或生产监控。
- 不在本阶段重构全部登录鉴权；但上线阿里云前必须把“客户端直接传 openid”升级为服务端会话令牌，不能把当前方式直接用于生产。
- 游客可以浏览词库，但不能保存个人学习、收藏、错词或统计数据。

## 3. 已选方案与备选方案

### 方案 A：独立学习进度表（已选）

新增 `user_word_progress`，只负责已学习状态；在现有 `wrong_words` 中增加掌握状态。收藏继续由 `vocabulary` 保存。

优点：改动范围小，职责清晰，能复用现有功能和数据。缺点：个人词汇状态分布在三张关系表中，但每张表含义单一，当前规模可接受。

### 方案 B：综合状态表（未选）

用一张表统一保存学习、收藏、错词和掌握状态。结构集中，但必须迁移并重写已有收藏和错题逻辑，风险和工作量更高。

### 方案 C：本地缓存后批量同步（未选）

继续把状态存在设备，定期上传 MySQL。多设备或离线修改时会出现覆盖与冲突，不符合“登录后数据可靠保存”的目标。

## 4. 数据库设计

开发环境数据库名称统一为当前后端实际使用的 `word_db`。`word.sql`、数据库导入说明和后端配置必须统一，不能再同时出现 `beibei_word` 与 `word_db` 两个名称。

### 4.1 新表 `user_word_progress`

| 字段 | 类型 | 规则 | 含义 |
|---|---|---|---|
| `user_id` | `INT UNSIGNED` | 联合主键、外键 | 用户 |
| `word_id` | `INT UNSIGNED` | 联合主键、外键 | 单词 |
| `learned_at` | `DATETIME` | 非空 | 首次或最近一次标记已学习时间 |
| `updated_at` | `DATETIME` | 非空、自动更新 | 最后修改时间 |

表中存在 `(user_id, word_id)` 记录即表示已学习；标记未学习时删除该记录。不增加可以互相矛盾的 `learned` 布尔字段。

外键删除规则：用户或单词删除时，对应进度级联删除。

### 4.2 修改 `wrong_words`

新增字段：

| 字段 | 类型 | 默认值 | 含义 |
|---|---|---|---|
| `mastered` | `TINYINT(1)` | `0` | 是否已掌握 |
| `mastered_at` | `DATETIME NULL` | `NULL` | 最近一次标记已掌握时间 |

取消掌握时设 `mastered=0`、`mastered_at=NULL`，不删除错词记录；用户主动从错题本删除时才删除记录。

标记已掌握后仍保留错词历史，但首页和个人统计的“错词数量”只统计 `mastered=0` 的未掌握错词。

### 4.3 脚本策略

- 更新主初始化脚本，使全新数据库直接得到最终结构。
- 单独提供一次性迁移脚本，用于升级当前已有数据，不删除 `words`、`users`、`vocabulary`、`wrong_words`、`checkins` 或 `pk_records`。
- 迁移前先只读检查表和字段；实施时不得通过重建数据库来掩盖迁移问题。

## 5. 后端接口设计

所有个人接口继续基于登录用户身份；本地阶段沿用现有 openid 传递方式，生产部署前另行升级会话鉴权。

### 5.1 学习进度

- `PUT /api/progress/{wordId}`：标记已学习；重复调用保持成功，不产生重复记录。
- `DELETE /api/progress/{wordId}`：标记未学习；记录不存在时仍返回成功。
- `GET /api/words`：当 `filter=learned` 或 `filter=unlearned` 时，服务端按 `user_word_progress` 查询，不再接收客户端 `learnedIds`。

未登录用户请求 `learned/unlearned` 筛选或修改进度时返回明确的未登录错误，不返回伪造的空结果。

### 5.2 错词掌握状态

- `PUT /api/wrong_words/{wordId}/mastered`，请求体 `{ "mastered": true|false }`。
- 仅允许修改当前用户已经存在的错词；不存在时返回 404，不自动创建错词。
- 错题本列表继续支持按 `mastered=true|false` 筛选，并返回 `mastered`、`masteredAt`。

### 5.3 统计

个人统计中的已学习数量从 `user_word_progress` 统计，错词数量只统计 `wrong_words.mastered=0`，收藏数量从 `vocabulary` 统计。前端不得再把本地缓存数量与服务端数量拼接成统计结果。

## 6. 前端业务流程

### 6.1 登录

1. 用户通过微信登录。
2. 后端使用微信 code 换取 openid，并在 `users` 中创建或更新用户。
3. 小程序保存当前登录会话信息。
4. 登录完成后重新加载首页摘要和个人统计。

本机调试微信登录仍要求电脑能够访问微信登录服务，并且 AppID/AppSecret 配置有效。

### 6.2 标记学习状态

1. 用户从首页或词库进入单词卡。
2. 点击“标记已学习”时先发送服务端请求。
3. 服务端成功后更新界面，并让该词从“未学习”筛选中消失、出现在“已学习”筛选中。
4. 请求失败时保持原状态并显示错误，不做假成功或静默写入本地缓存。
5. 再次点击可取消已学习，调用删除接口。

### 6.3 错词掌握状态

1. 闯关或好友 PK 答错时加入 `wrong_words`；重复答错同一单词只保留一条记录，并重置为未掌握。普通单词学习不写入错题本。
2. 用户在错题本切换“已掌握”时调用服务端接口。
3. 成功后更新列表；失败时恢复原状态并提示。
4. “未掌握/已掌握”筛选都从服务端结果生成。

### 6.4 游客边界

游客可查看四级/六级词库和单词详情。点击学习状态、收藏、错词、闯关提交、打卡、PK 或个人统计时，统一提示先登录；不以本地缓存冒充已保存数据。

## 7. 配置与未来迁移

- 本机 MySQL、后端和小程序分别通过 `127.0.0.1:3306`、`127.0.0.1:8081` 调试。
- 真机不能访问电脑的 `127.0.0.1`；真机联调时另行使用电脑局域网 IP。
- 阿里云部署时保持数据库名、表结构和接口路径不变，只调整数据库连接、后端域名、HTTPS 和微信合法域名。
- 数据库密码和微信 AppSecret 不得提交到公开仓库或写入交付截图；当前明文配置在上线前需要移出通用配置并轮换密钥。

## 8. 错误与一致性规则

- 写操作以 MySQL 成功为准，前端不提前显示成功状态。
- 新增/删除进度和修改错词掌握状态必须具备幂等性。
- 用户只能读写自己的进度；至少用 `user_id + word_id` 作为查询条件。
- 不使用空字符串、0 或假列表掩盖缺失用户、缺失单词或无效登录。
- 控制器负责参数边界和 HTTP 状态，服务层负责业务规则，数据库负责唯一性和外键约束。

## 9. 验收标准

1. 用户 A 登录后标记一个单词已学习，MySQL 出现唯一进度记录。
2. 重新编译小程序、重启 Java、清除小程序缓存并重新登录后，该单词仍显示已学习。
3. 词库“已学习/未学习”分页总数和列表正确，切换四级/六级不会串数据。
4. 同一操作重复执行不会出现重复数据或 500 错误。
5. 用户 A 的学习状态不会出现在用户 B 的账号中。
6. 错词标记已掌握后，重启并重新登录仍保留；取消掌握后回到未掌握列表。
7. 游客尝试保存个人状态时会收到登录提示，数据库不写入匿名数据。
8. 收藏、生词本、错题收录、闯关提交、打卡和 PK 的现有数据未被迁移脚本删除。
9. 闯关和 PK 答错都会写入错题本；普通单词学习不会写入错题本；重复答错会把已掌握错词重置为未掌握。
10. 首页和个人统计只显示未掌握错词数量，已掌握记录仍可在错题本筛选查看。
11. 后端自动测试覆盖进度新增、删除、重复操作、用户隔离、错误单词和错词掌握状态。
12. 前端检查覆盖成功更新、请求失败不改状态、未登录提示以及筛选参数。

## 10. 实施顺序

1. 备份并只读核对当前 `word_db` 表结构和数据量。
2. 编写并验证数据库迁移测试，再执行迁移；不读取或上传设备里的旧学习状态。
3. 实现后端实体、Mapper、Service 和 Controller 测试及接口。
4. 将前端学习状态与错词掌握状态从本地缓存切换为服务端接口。
5. 验证首页、词库、单词卡、错题本和个人统计的完整闭环。
6. 回归收藏、闯关、打卡和 PK。
7. 用户在微信开发者工具中验收本阶段后，再进入下一个基础功能。

## 11. 留给实现阶段的局部决定

- Java 类与 Mapper 的具体命名遵循现有项目风格。
- SQL 索引名称、测试夹具和错误文案可由实现者确定，但不得改变上述接口语义和验收标准。
- 页面视觉沿用现有设计，仅在现有按钮上连接真实状态，不新增页面或卡片。
